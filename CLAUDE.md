# Pi-hole VPN Droplet

A hardened, privacy-focused DigitalOcean Marketplace image that bundles Pi-hole v6 (ad blocking), WireGuard (VPN), and Unbound (recursive DNS resolver). Built for personal privacy: full-tunnel VPN, local DNS, ad/tracker blocking, and minimal fingerprint visibility.

Packer builds the snapshot. Terraform provisions the Droplet. Cloud-init scripts configure everything on first boot.

## Read first: safety and intent

These are deliberate design decisions, not bugs. Do not "fix" them without understanding why.

- **Never commit WireGuard private keys or PSKs.** All keys are generated at runtime via `wg genkey` and `wg genpsk`. The patterns are in `.gitignore`. Confirm before adding anything that touches `*.key`, `*.conf` (WireGuard config), or `*.pem`.
- **Never commit admin passwords.** Pi-hole admin passwords are generated randomly at first boot and stored at `/root/.pihole-admin-pass` (mode 0600) on the Droplet. They are never in git.
- **Admin UI binds to wg0 only.** The Pi-hole web interface must not be reachable from the public interface. Removing this restriction exposes the admin panel to the internet.
- **Pi-hole v6 uses pihole.toml, not setupVars.conf.** All runtime configuration targets `/etc/pihole/pihole.toml`. Do not introduce legacy v5 flat-file config writes.
- **No lighttpd.** Pi-hole v6 uses the embedded FTL web server. Do not add lighttpd or PHP dependencies.
- **WireGuard PSK is required for all peers.** Every client peer gets a pre-shared key generated by `wg genpsk`. Do not create peers without one.
- **SSH hardening is intentional.** Key-only authentication and idle timeout are applied at first boot. Do not weaken these settings.

## Validation: the closed loop

`./validate.sh` is the single source of truth for "is this working." It runs shellcheck on all scripts, terraform fmt and validate, optional packer validate, and a secret scan.

- Exit code 0 means every check passed. Non-zero means the first failure, with the reason.
- It runs unattended. Run it, read the result, fix, repeat.
- **Reach `./validate.sh` exit 0 before any commit. No exceptions.**

```bash
./validate.sh                    # shellcheck + terraform + secret scan, exit 0 = pass
DO_PAT=<token> ./validate.sh    # also runs packer validate
```

## Planning: specs first

Feature work starts from a spec, not from a prompt. This keeps handoffs clean and the plan reviewable before any code changes.

Two artifacts, two trust levels:
- **`proposals/`**: candidate ideas, mostly agent-authored via `/suggest`. `Status: proposed`. NOT build-ready. Never implemented directly.
- **`specs/`**: decided, build-ready work you authored or promoted. `Status: ready`. What `/implement` builds.

The agent may propose freely. Only you turn a proposal into a spec. To promote one, run `/plan proposals/NNN-name.md`.

Specs ready to build now: none. Promote a `proposals/` candidate with `/plan` to queue the next build.

Drafted, pending a scope or dependency decision (not build-ready): none yet.

Shipped: none yet. The initial modernization commit (Debian 12, Pi-hole v6, security hardening) is the baseline.

## Skills (the workflow)

Reusable workflow prompts live in `.claude/skills/<name>/SKILL.md`. Invoke with `/name`. Run `/workflow` anytime to print this map. Each skill ends by naming the next step.

In order:

| # | Skill | Does | Auto-invoke |
| --- | --- | --- | --- |
| 1 | `/suggest` | Write a candidate improvement to `proposals/` | Yes |
| 2 | `/clarify [target]` | Ask focused questions to tighten a proposal, spec, or idea | No |
| 3 | `/plan [desc \| proposal]` | Author a build-ready spec in `specs/`, or promote a proposal | No |
| 4 | `/tasks [spec]` | Break the spec into an ordered task list with parallel markers | No |
| 5 | `/implement [spec]` | Build a ready spec, drive `./validate.sh` to exit 0 | No |
| 6 | `/validate` | Closed loop: shellcheck, terraform, secret scan | Yes |
| 7 | `/review` | Review changes, triage findings, capture backlog to `proposals/` (never edits code) | Yes |
| 8 | `/ship [message]` | Validate, sync README + CLAUDE.md to the change, then commit (push stays manual) | No |

Typical path: `/clarify` then `/plan` then `/tasks` then `/implement` then `/review` then `/ship`. The agent runs `/validate` itself after changing code, and may drop ideas into `proposals/` via `/suggest` at any time. New here? Run `/workflow`.

## Review triage

Findings from `/review` do not all block a ship. Sort by the scope test: did this change introduce the finding, or did it merely sit near it?

| Finding | Action |
| --- | --- |
| Blocker, or should-fix introduced by this change | Fix before `/ship` |
| One-line nit on a file this change already touches | Fix if quick; `/review` also files it so it is never lost |
| Should-fix or nit that is pre-existing or out of scope | Backlog: `/review` captures it to `proposals/`, keep moving |

`/review` captures every finding except the must-fix list to `proposals/` automatically. The review report ends with a findings ledger that lists every finding and where it went. The bar to ship is a clear must-fix list, not a clean nit list.

## Build and run

```bash
# Validate scripts and config
./validate.sh

# Build Packer snapshot (requires DO_PAT env var)
packer build -var "do_token=${DO_PAT}" main.pkr.hcl

# Provision Droplet (requires image ID from Packer output)
cd terraform
terraform init
terraform apply -var "do_token=${DO_PAT}" -var "image=<snapshot-id>"

# Test scripts locally (requires shellcheck)
shellcheck scripts/*.sh
```

## Conventions

- **No external package managers beyond apt.** All dependencies are Debian packages. No pip, npm, or Go modules.
- **shellcheck clean.** All `.sh` files must pass `shellcheck -x`. `validate.sh` enforces this.
- **No hardcoded secrets.** Keys and passwords are generated at runtime. The `.gitignore` and validate.sh secret scan back this up.
- **Prose, comments, and docs style** (applies to anything you write in this repo):
  - No em dashes. Use commas or parentheses.
  - Never use the word "ensure." Use "confirm," "make sure," or rephrase.
  - Active voice. Direct, business-like language. No marketing inflation.
  - Tables and short sections over long paragraphs.
- **Decisions:** when options exist, pick one and state the assumption rather than listing alternatives.
- **Pi-hole v6:** all config writes target `/etc/pihole/pihole.toml`. If you need to modify it, use `pihole-FTL --config key value` or a POSIX-compatible sed/awk rewrite.
- **WireGuard port:** default is 51820, controlled by `WG_PORT` environment variable in wg-setup.sh. Alternative ports (443/UDP, 53/UDP) are documented in README.
